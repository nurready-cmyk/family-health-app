# PRD — Health OS (Telegram-бот)
**Product Requirements Document**
Версия 1.0 · Июль 2026

---

## 1. Обзор проекта

### 1.1 Идея
Персональная медицинская операционная система семьи в формате Telegram-бота. Каждый член семьи (у кого есть Telegram) может голосом, фото или текстом сообщать боту о своём здоровье — бот распознаёт, структурирует и сохраняет данные, а дальше на их основе даёт рекомендации. Дети и другие члены семьи без Telegram тоже учитываются в системе — за них данные вносит администратор.

### 1.2 Предыстория и связь с другими частями репозитория
В этом же репозитории уже есть:
- `index.html` и другие корневые файлы — PWA «Здоровье семьи» (localStorage, без сервера, см. корневой `PRD.md`).
- `telegram-bot/` — первая версия Telegram-бота на Google Apps Script + Google Sheets (простой rule-based движок, без LLM, без ролей).

**Health OS (`health_os_bot/`) — следующая, более зрелая итерация**: тот же смысл (семейный трекер здоровья через Telegram), но с Clean Architecture, реальными ролями пользователей, распознаванием голоса/фото через AI и явным заделом под будущий переход в коммерческий SaaS. Она не удаляет и не изменяет `telegram-bot/` — это параллельный, более продвинутый путь развития продукта.

### 1.3 Цель продукта
Бот снимает с семьи ручной труд по вводу и структурированию медицинских данных (голосом или фото — не только формами) и превращает их в базу, на основе которой можно строить рекомендации, отслеживать динамику и, в перспективе, продавать это как сервис другим семьям.

### 1.4 Долгосрочное видение (пост-MVP)
Продукт закладывается так, чтобы три вещи можно было заменить/масштабировать без переписывания бизнес-логики:
1. Google Sheets → PostgreSQL (или любая другая СУБД) — только слой `database/`.
2. OpenAI (GPT-4o-mini / GPT-4o) → локальная LLM (например, через Ollama) — только слой `services/`.
3. Фиксированная семья → произвольное число независимых семей (мультитенантность) — модель ролей и `Family_Members` уже спроектирована с этим прицелом (динамическое добавление членов семьи с первого дня, а не хардкод).

## 2. Пользователи и роли

| Роль | Кто | Права |
|---|---|---|
| `admin` | Муж | Вносит данные за любого члена семьи (выбор через inline-кнопки), может добавлять новых членов семьи прямо из бота |
| `user` | Жена | Пишет боту сама, со своего Telegram-аккаунта; вносит данные только за себя |
| Член семьи без Telegram | Дети и т.д. | Не пишут боту; все данные за них вносит `admin`. Существуют в системе как запись в `Family_Members`, но не в `Users` |

**Идентификация:** каждое входящее сообщение проверяется по `tg_id` в листе `Users`. Роль определяет, чьи `family_member_id` доступны для записи (админу — все, юзеру — только свой).

**Добавление члена семьи:** доступно только `admin`, через команду/кнопку в боте — не требует ручного редактирования Google Sheets. Создаёт новую строку в `Family_Members`; если у нового члена есть свой Telegram, дополнительно создаётся строка в `Users`.

## 4. Архитектура (Clean Architecture / паттерн Репозиторий)

```
Telegram update
      │
      ▼
  handlers/   ── только парсинг апдейта и вызов core/, никакой бизнес-логики
      │
      ▼
   core/      ── Decision Engine: права доступа, сборка данных для сохранения,
      │           логика "что делать с извлечённым из LLM результатом"
      │
      ├──────────────► services/  ── OpenAI (GPT) + faster-whisper,
      │                              возвращают core/ уже готовый результат
      │
      └──────────────► database/  ── репозитории (Users, FamilyMembers, Logs,
                                      MedicalData, KnowledgeBase). Единственное
                                      место, где импортируется gspread.
```

**Правило:** `handlers/` и `core/` никогда не импортируют `gspread`, `openai` или `faster_whisper` напрямую — только интерфейсы `database/` и `services/`. Замена Google Sheets на PostgreSQL — это переписывание реализации внутри `database/`, сигнатуры репозиториев не меняются.

### Правила кода (обязательны, проверяются автоматическим аудитом)
- Никаких глобальных переменных.
- Роутеры (`handlers/`) отделены от бизнес-логики (`core/`).
- Каждая строка и каждый файл заканчиваются пустой строкой (trailing newline) — без исключений.
- Никаких абсолютных локальных путей — всё через переменные окружения, готово к деплою в любой момент.

## 5. Схема базы данных (Google Sheets, 5 листов)

Во все листы добавлена скрытая колонка `id` (UUID) — не видна пользователю в интерфейсе, но даёт репозиториям `update_by_id` / `delete_by_id` и безболезненный перенос на Postgres (первичный ключ с самого начала).

### 5.1 `Family_Members` — реестр всех членов семьи (в т.ч. без Telegram)
| Колонка | Тип | Описание |
|---|---|---|
| `id` | UUID | Первичный ключ |
| `name` | text | Имя |
| `gender` | male/female | Для норм анализов и т.п. |
| `birth_year` | int | Год рождения |

### 5.2 `Users` — только те, у кого есть Telegram-аккаунт
| Колонка | Тип | Описание |
|---|---|---|
| `id` | UUID | Первичный ключ |
| `tg_id` | int | Telegram user id |
| `name` | text | Имя |
| `role` | admin/user | Права доступа |
| `family_member_id` | UUID (FK) | Ссылка на `Family_Members.id` |

### 5.3 `Logs` — ежедневные метрики
| Колонка | Тип | Описание |
|---|---|---|
| `id` | UUID | Первичный ключ |
| `date` | date | Дата записи |
| `family_member_id` | UUID (FK) | За кого запись |
| `metric_type` | energy/sleep/food/workout | Тип метрики |
| `value` | text/number | Значение |
| `notes` | text | Заметка |

### 5.4 `Medical_Data` — анализы, обследования, приёмы врачей
| Колонка | Тип | Описание |
|---|---|---|
| `id` | UUID | Первичный ключ |
| `date` | date | Дата события |
| `family_member_id` | UUID (FK) | Чьи данные |
| `event_type` | text | Анализ / приём врача / обследование |
| `summary` | text | Саммари от GPT-4o или ручной ввод |
| `document_url` | url | Ссылка на скан в Google Drive |

### 5.5 `Knowledge_Base` — личные правила («обучение» бота)
| Колонка | Тип | Описание |
|---|---|---|
| `id` | UUID | Первичный ключ |
| `family_member_id` | UUID (FK) | К кому относится правило |
| `rule_text` | text | Например: «если гемоглобин низкий — мне лично помогает больше гречки, меньше кофе» |
| `priority` | int | Приоритет при конфликте с общими рекомендациями (личные правила проверяются первыми) |

## 6. Функциональные сценарии (UX)

### 6.1 Идентификация и права
Бот проверяет `tg_id` в `Users`. `admin` получает inline-выбор «за кого вносим данные» (все строки `Family_Members`), `user` работает только со своим `family_member_id` без права выбора.

### 6.2 Добавление члена семьи (только `admin`)
Команда/кнопка «Добавить члена семьи» → бот спрашивает имя, пол, год рождения → создаёт строку в `Family_Members`. Если у человека есть свой Telegram — дополнительно создаётся строка в `Users` с ролью `user`.

### 6.3 Мультиформатный ввод
Пользователь может прислать:
- **Текст** — напрямую в `core/` на структурирование (без LLM, если формат уже понятен, либо через GPT-4o-mini).
- **Голосовое сообщение** — обрабатывается локально.
- **Фото** (скан анализа/заключения) — обрабатывается через vision-модель.

### 6.4 Обработка голоса
1. Бот скачивает голосовое сообщение.
2. Транскрибирует **локально** через `faster-whisper` (без обращения к интернету).
3. Передаёт транскрипт в `gpt-4o-mini` для извлечения структуры (`metric_type`, `value`, `notes` или данные для `Medical_Data`).
4. Показывает пользователю карточку подтверждения: «Понял: гемоглобин = 135, сохранить?» с кнопками **Да** / **Исправить**.
5. Только после «Да» — запись через `database/` в соответствующий лист.

### 6.5 Обработка фото
1. Бот скачивает фото.
2. Загружает оригинал в Google Drive (тот же сервис-аккаунт, папка проекта) — получает `document_url`.
3. Отправляет изображение в `gpt-4o` с просьбой сделать саммари и выделить отклонения от нормы.
4. Показывает карточку подтверждения (саммари + предложенные поля) с кнопками **Да** / **Исправить**.
5. После подтверждения — запись в `Medical_Data` с `summary` и `document_url`.

### 6.6 Принцип подтверждения (обязателен для любых LLM-данных)
Ни один результат распознавания голоса или фото не попадает в базу без явного подтверждения пользователем. Это защита от ошибок Whisper/GPT в медицинских данных — цена лишнего тапа по кнопке значительно ниже цены неверной записи в истории здоровья.

### 6.7 Личные правила (`Knowledge_Base`)
Пользователь может «обучить» бота своим правилом (аналогично `PersonalRules` в `telegram-bot/`): бот сначала проверяет `Knowledge_Base` конкретного `family_member_id`, и только потом — общую базу рекомендаций.

## 7. AI/LLM-интеграции и их стоимость

| Задача | Модель | Стоимость | Примечание |
|---|---|---|---|
| Расшифровка голоса | `faster-whisper` (base/small) | Бесплатно | Работает локально, без интернета |
| Извлечение структуры из текста | `gpt-4o-mini` | Платно (доли цента/запрос) | Осознанно принято вместо полностью локальной LLM ради качества MVP |
| Саммари фото анализов | `gpt-4o` (vision) | Платно (немного дороже mini) | То же |

`services/` абстрагирует провайдера LLM за единым интерфейсом (например, `TextExtractionService`, `ImageSummaryService`) — переход на локальную LLM (Ollama + llama3/qwen и т.п.) в будущем не потребует изменений в `core/`.

```
health_os_bot/
├── bot.py                    ← точка входа: Bot/Dispatcher, DI, middleware, роутеры, polling

├── requirements.txt
├── .env.example
├── .gitignore                 ← .env, credentials.json, venv, __pycache__
├── PRD.md                     ← этот документ
├── handlers/                   ← роутеры aiogram (только парсинг апдейта + вызов core/)
│   ├── __init__.py             ← get_routers() — единая точка регистрации
│   ├── states.py               ← FSM StatesGroup для многошаговых диалогов
│   ├── keyboards.py             ← инлайн-клавиатуры (пол, члены семьи, тип метрики)
│   ├── middlewares.py            ← AccessMiddleware — резолвит AccessContext на каждый апдейт
│   ├── registration.py            ← /start, bootstrap admin, /add_family_member
│   └── logs.py                     ← /log — ручной ввод ежедневных метрик
├── core/                        ← Decision Engine: права доступа, бизнес-правила
│   ├── __init__.py
│   ├── exceptions.py             ← AccessDeniedError
│   ├── access.py                  ← AccessService/AccessContext — кто ты и за кого можешь писать
│   ├── family_members.py           ← FamilyMemberService — добавление членов семьи + bootstrap admin
│   └── logs.py                      ← LogService — запись метрики с проверкой прав
├── database/                    ← паттерн Репозиторий, единственный слой с gspread
│   ├── __init__.py                ← build_repositories() — composition root
│   ├── models.py                   ← доменные dataclass'ы + enum'ы Role/Gender/MetricType
│   ├── interfaces.py                ← абстрактные ABC-репозитории (контракт)
│   ├── sheets_client.py              ← GoogleSheetsClient + SheetRowStore (единственное место с gspread)
│   ├── sheets_repositories.py          ← реализации интерфейсов поверх Google Sheets
│   └── setup.py                        ← `python -m database.setup` — создание листов
└── services/                    ← OpenAI (GPT) + faster-whisper, скрыты за интерфейсом
    ├── __init__.py
    ├── models.py                  ← ExtractedMetric — результат извлечения, ещё не сохранённый
    ├── exceptions.py               ← TranscriptionError, ExtractionError
    ├── interfaces.py                ← абстрактные TranscriptionService, MetricExtractionService
    ├── faster_whisper_transcription.py  ← FasterWhisperTranscriptionService (локально, бесплатно)
    └── openai_text_extraction.py         ← OpenAIMetricExtractionService (gpt-4o-mini, платно)
```

## 10. Нефункциональные требования

| Параметр | Требование |
|---|---|
| Бюджет | Telegram Bot API, Google Sheets, Google Drive, `faster-whisper` — бесплатно. OpenAI (`gpt-4o-mini`, `gpt-4o`) — минимальные реальные расходы, приняты осознанно |
| Готовность к облаку | Никаких абсолютных локальных путей, вся конфигурация через `.env` |
| Приватность | Доступ сервис-аккаунта ограничен конкретной таблицей и папкой Drive проекта; медицинские данные не покидают Google-аккаунт семьи и OpenAI (только для структурирования/саммари) |
| Формат кода | Trailing newline на каждом файле — обязательное условие автоматического аудита форматирования |
| Расширяемость | Смена БД, LLM-провайдера или переход на мультисемейность не должны требовать изменений вне одного слоя (`database/`, `services/` или модели ролей соответственно) |

## 11. Что не входит в MVP
- Миграция на PostgreSQL (архитектура готова, но не реализована)
- Локальная LLM вместо OpenAI (архитектура готова к замене, но не реализована)
- Веб-интерфейс / SaaS-онбординг для сторонних семей
- Автоматический парсинг PDF-бланков (только фото через vision-модель)
- Уведомления/триггеры по расписанию (ежедневный чек-ин, еженедельный отчёт) — можно перенести идею из `telegram-bot/Triggers.gs`, но не в этом этапе
